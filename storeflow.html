StoreFlow

Retail sales reconciliation with a record of what arrived, what loaded, and what needs investigation.

The problem

A sales dashboard is only useful if its underlying records can be explained. Store files may contain duplicates, unknown stores or products, malformed dates, and inconsistent amounts. A load that finishes successfully can still leave data-quality issues unresolved.

My contribution

I built this portfolio project to demonstrate the complete path from CSV ingestion to reporting: a relational schema, Python loading and transformation scripts, row-level rejection records, eight summary checks, pipeline run logging, and a Streamlit dashboard.

The scenario uses generated sales from six fictional stores. It draws on the kinds of file and integration problems found in retail operations without using employer data.

Approach & architecture

  1. 1. IngestCSV files → raw staging, with file and row provenance
  2. 2. TransformReference checks → typed facts or row-level rejects
  3. 3. InspectSummary checks + run logs → Streamlit dashboard

PostgreSQL separates store, product, and department dimensions from stg_sales_raw, fact_sales, rejected_sales_rows, validation_results, and pipeline_run_log.

Decisions and tradeoffs

  • Keep raw values as text. Malformed inputs can reach staging for inspection before conversion to dates, integers, and decimal amounts.
  • Separate rejected rows from accepted facts. Source file, source row number, run ID, and a rejection reason make problems traceable without putting those rows into reporting.
  • Use database uniqueness for duplicates. A transaction-line key with ON CONFLICT DO NOTHING prevents repeat fact inserts. Skipped duplicates are counted separately from row-level validation rejects.
  • Use explicit batch steps. Python orchestrates ingestion, transformation, and validation. This keeps the project approachable, but it does not yet provide a production scheduler, retry policy, or complete transaction rollback across all steps.

What the validation exceptions mean

The generator deliberately injects duplicate lines, invalid stores, unknown products, incorrect amounts, negative quantities, and malformed dates. Transformation rejects invalid records; the database skips duplicate fact rows. Eight separate summary checks inspect the run.

“5 failed” is a data-quality result, not a test-suite result.

Four failed checks identify injected input issues. The fifth is a raw-to-final total mismatch: the current staging-total calculation includes otherwise valid duplicates, while the fact table retains one copy. This is a reconciliation limitation that still needs correction.

Error handling

Row validation raises descriptive errors for missing fields, invalid references, conversion failures, negative values, and amount mismatches. These are saved with source provenance. Pipeline-level exceptions are caught and an attempt is made to record failure in the run log.

Run completion and data quality are distinct: the current pipeline does not derive its final run status from the summary check results. A completed run can still require investigation.

Dashboard & sample results

The dashboard provides business performance, data quality, and record explorer views. Accepted records can be traced to their source file and pipeline run.

The documented 30-day, six-store run processes 180 files and stages 16,427 rows. It loads 16,229, records 165 row-level rejects, and skips 33 duplicates: 198 excluded rows in total. The displayed acceptance rate is 98.8%.

These results demonstrate ingestion, traceability, and exception visibility. They do not establish production scale, business savings, or that every validation rule passes.

Limitations & supporting evidence

  • Reconciliation needs the same acceptance and deduplication rules as the fact load. Reprocessing an existing batch also needs clearer per-run accounting.
  • Completeness is checked only for dates present in staging. A date missing from every store’s input is outside that check’s current scope.
  • The published schema is missing the definition of validation_results even though it creates indexes on that table. A fresh database setup needs that definition before the full application can run.
  • The repository’s test file is empty. There is no established automated regression suite or production reliability claim.
  • Public deployment, authentication, alerting, and automated archiving are future work. No live demo is linked.
